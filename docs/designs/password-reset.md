## Problem Statement

`src/app/(auth)/forgot-password/page.tsx`는 UI 샘플이다. 제출하면 `setTimeout` 1초 뒤 무조건 "메일을 확인해 주세요"를 보여주고 실제 요청은 없다(18행 TODO). 메일 링크가 도착할 `/reset-password` 페이지도 없어서, 발송만 연동하면 사용자는 링크를 눌러도 갈 곳이 없다. 목표는 메일 발송부터 새 비밀번호 저장까지 한 번에 동작하는 전체 흐름이다.

## What Makes This Cool

레포의 첫 `supabase.auth` 사용이다. 서버 코드, 라우트 핸들러, 새 의존성 없이 이미 있는 `getSupabase()` 하나로 실제 메일이 오가는 인증 흐름이 생긴다. 배포 URL에서 팀원 이메일 계정으로 바로 시연할 수 있다(전제 4).

## Constraints

- Next.js 16 App Router, 기존 페이지는 `"use client"` CSR. 서버 컴포넌트·미들웨어 추가 없음.
- `@supabase/supabase-js@2.117.3`, `createClient` 기본 `flowType: 'implicit'`(auth-js GoTrueClient.js:21 확인). 재설정 링크는 `/reset-password#access_token=...&type=recovery`로 돌아오고, `detectSessionInUrl` 기본값이 true라 클라이언트가 해시에서 세션을 자동으로 세운다.
- 로그인·회원가입 페이지 없음. "로그인으로 돌아가기"는 `/`로 이동한다.
- import 규칙: `app → features → shared`. `app`에서 `@/shared/lib/supabase`를 직접 import하는 것은 허용된다.
- 스타일은 기존 `@theme` 토큰 클래스만 사용한다.

## Premises (모두 동의)

1. 범위는 전체 흐름: `/forgot-password` 발송 + 새 `/reset-password` 저장.
2. 가입 여부를 드러내지 않는다. 성공 화면은 이메일 존재 여부와 상관없이 같다. 요청 제한(429)도 가입된 이메일에서만 나므로 성공 화면으로 처리하고, 네트워크·설정 오류만 오류로 표시한다.
3. 로그인·회원가입은 범위 밖. 테스트 계정은 Supabase 대시보드에서 만든다. 완료 후 `/`로 보낸다.
4. 대시보드 설정은 사용자가 직접 한다: Auth → URL Configuration → Redirect URLs에 `http://localhost:3000/reset-password`, `https://textbook-store.vercel.app/reset-password` 추가. Site URL은 운영 URL로 둔다. Vercel 프리뷰 배포에서는 재설정 흐름을 지원하지 않는다(redirectTo가 거부돼 Site URL로 돌아감). 기본 SMTP를 그대로 쓰므로 **메일은 Supabase 조직 팀원 이메일로만 발송되고** 시간당 발송량도 적다. 따라서 테스트 계정은 팀원 이메일로 만들고, 외부인 대상 시연은 커스텀 SMTP를 연결한 뒤에 한다.
5. 만료되거나 잘못된 링크로 `/reset-password`에 들어오면 폼 대신 안내와 `/forgot-password` 링크를 보여준다.

## Approaches Considered

### Approach A: 페이지에 직접 연동 (선택)

두 페이지 파일에서 `getSupabase().auth`를 직접 호출. 파일 2개, 새 추상화 없음.

### Approach B: features/auth 모듈 (보류)

`features/auth/{api.ts, components, index.ts}`로 분리. 지금은 호출처가 하나뿐이라 보류하고, 로그인이 추가돼 auth 호출처가 둘 이상이 되면 옮긴다.

### Approach C: 6자리 OTP 코드 (기각)

`verifyOtp({ type: 'recovery' })`로 링크 없이 같은 페이지에서 진행. 메일 템플릿 수동 변경과 기존 "재설정 링크" UI 문구 수정이 필요해서 기각.

## Recommended Approach

Approach A.

### 1. `src/app/(auth)/forgot-password/page.tsx` (수정)

- `status` 타입에 `"error"` 추가. 오류 문구는 `errorMessage` state 하나로 관리한다.
- `handleSubmit`의 `setTimeout`과 TODO 주석, 파일 상단 "화면 확인용 샘플" 주석을 지운다. 그 자리에서 다음을 실행한다.
  ```ts
  const { error } = await getSupabase().auth.resetPasswordForEmail(email, {
    redirectTo: `${window.location.origin}/reset-password`,
  });
  ```
- 결과 처리 (호출 전체를 `try/catch`로 감싼다):
  - `error` 없음 또는 `error.status === 429` → 기존 `"sent"` 화면. 이 판정은 `src/app/(auth)/forgot-password/request-result.ts`의 `isResetRequestAccepted(error)`로 분리하고 `request-result.test.ts`에 3행(null → true, 429 → true, 500 → false)을 둔다(Eng review D5). 가입되지 않은 이메일은 Supabase가 성공을 돌려주고, 429(`over_email_send_rate_limit`)는 최근에 요청한 가입 이메일에서만 나온다. 그래서 429를 따로 표시하면 가입 여부가 드러난다(전제 2). 대신 `"sent"` 화면 설명에 "메일이 오지 않으면 잠시 후 다시 시도해 주세요."를 한 줄 덧붙인다.
  - 그 밖의 `error`, 또는 `catch`로 잡힌 예외(네트워크 실패, `getSupabase()`의 환경변수 누락) → "메일을 보내지 못했어요. 잠시 후 다시 시도해 주세요."
  - 오류일 때는 폼을 유지하고 버튼 아래에 `role="alert"`로 문구를 보여준다. 입력값을 바꾸거나 다시 제출하면 문구를 지운다.
- `"sent"` 화면에 "다른 이메일로 다시 받기" 버튼을 둔다. 누르면 status를 `idle`로 되돌리고 입력한 이메일은 유지한다. 오타 이메일·429로 메일을 못 받은 사용자의 재시도 경로이고, `cacheComponents`가 sent 상태를 보존해 다른 페이지를 다녀와도 완료 화면이 남는 경우의 탈출구다(Eng review D10, Codex #3).
- 이메일 앞뒤 공백은 `email.trim()`으로 제거해서 보낸다.

### 2. `src/app/(auth)/reset-password/page.tsx` (신규)

forgot-password와 같은 레이아웃(Header, `max-w-[400px]` 컨테이너, 제목·설명, 입력, 버튼, Footer)을 쓴다.

상태: `"checking" | "ready" | "invalid" | "saving" | "done"` + `errorMessage`.

- **세션 확인 (`checking`)**: 화면에는 제목 없이 "링크를 확인하는 중..."(`role="status"`)만 보여준다. 마운트 시 `useEffect`에서 다음을 순서대로 실행하고, 전체를 `try/catch`로 감싸 예외가 나면 `invalid`로 보낸다. `cacheComponents`가 페이지를 `<Activity>`로 숨겼다가 다시 보일 때 effect가 재실행되므로, `checkedRef`로 한 번만 실행한다(다시 보일 때는 해시가 이미 지워져 있어 재판정하면 invalid가 됨. Eng review D9).
  1. **클라이언트를 만들기 전에** `window.location.hash`를 읽어 `type`과 `access_token`을 기록한다(`const params = new URLSearchParams(window.location.hash.slice(1))`). supabase-js는 해시를 처리한 뒤 지우므로(auth-js GoTrueClient.js:3334 `window.location.hash = ''`) 먼저 읽어 둔다.
  2. `const { data, error } = await recovery.auth.getSession()`. `recovery`는 1단계 직후 `createIsolatedSupabase()`로 만든 전용 클라이언트다(persistSession false, autoRefreshToken false, storageKey "sb-password-recovery"; ref에 보관, SSR에서 만들지 않음). 세션이 메모리에만 있어 다른 탭의 링크가 덮어쓰지 못하고 페이지를 떠나면 사라진다(Eng review D6, Codex #1). 이후 updateUser·signOut도 이 클라이언트로 호출한다. `getSession`은 클라이언트 초기화(URL 해시 처리 포함)가 끝날 때까지 기다린다(auth-js GoTrueClient.js:2413 `await this.initializePromise`).
  3. **`type === "recovery"`이고 `data.session?.access_token`이 해시의 `access_token`과 같을 때만** `ready`로 바꾼다. 이 판정은 `src/app/(auth)/reset-password/recovery.ts`의 `isRecoveryLink(hash, accessToken)`로 분리하고(page.tsx는 임의 export 불가), 해시 토큰이 비어 있으면 false로 처리한다(Eng review D4). 세션이 이번 URL에서 만들어졌다는 뜻이다. `#type=recovery`만 손으로 붙이면 토큰이 없거나 다르므로 통과하지 못한다. 그 밖의 경우는 모두 `invalid`다. invalid 경로에서는 signOut을 부르지 않는다. 전용 메모리 클라이언트라 이전 방문의 세션이 남지 않고, 이번 세션도 페이지를 떠나면 사라진다(Eng review D7, Codex #2: 기본 scope global 로그아웃 회피). 그래서 같은 브라우저를 쓰는 다른 사람이 메일 링크 없이 비밀번호를 바꿀 수 없다.
  - 해시에 `error`(예: `error_code=otp_expired`)가 있으면 `type=recovery`가 없고 세션도 생기지 않으므로 `invalid`가 된다.
- **`invalid`**: "링크가 만료됐거나 올바르지 않아요. 네트워크 상태를 확인하고 이 페이지를 새로고침해 보세요." + `/forgot-password`로 가는 "재설정 링크 다시 받기" 링크. (Eng review D2)
  - 한계: `_getUser` 네트워크 실패는 supabase-js가 예외 없이 `session: null`로 돌려줘 만료 링크와 구분할 수 없다(GoTrueClient.js:3320). 이때 해시는 지워지지 않으므로(지우기는 성공 후, :3334) 새로고침하면 같은 토큰으로 다시 시도된다. 메일 속 링크는 일회용이라 재클릭을 안내하지 않는다.
- **`ready`**: 새 비밀번호, 비밀번호 확인 두 입력(`type="password"`, `autoComplete="new-password"`, `minLength={6}`).
  - 버튼 활성 조건: 두 값이 같고 길이가 6 이상이며 `status !== "saving"`. 저장 중에는 버튼 문구를 "저장하는 중..."으로 바꾼다(forgot-password page.tsx:64 패턴, 더블클릭 시 두 번째 응답이 done 화면을 오류로 덮는 것을 막음. Eng review D3). 확인 값이 다르면 입력 아래에 "비밀번호가 일치하지 않아요."를 보여준다.
  - 6은 Supabase Auth 기본 최소 길이다. 대시보드에서 정책을 올리면 서버가 `weak_password`를 돌려주므로 아래 오류 매핑이 받아낸다.
- **저장 (`saving`)**: `await recovery.auth.updateUser({ password })`. `try/catch`로 감싸고, 예외는 아래 "그 밖" 문구로 처리한다.
  - `error.code === "same_password"` → "이전과 다른 비밀번호를 입력해 주세요."
  - `error.code === "weak_password"` → "더 안전한 비밀번호를 입력해 주세요."
  - 그 밖 → "비밀번호를 바꾸지 못했어요. 다시 시도해 주세요."
  - 오류일 때는 `ready`로 돌아가고 `role="alert"` 문구를 보여준다.
- **`done`**: 성공하면 `await recovery.auth.signOut()`으로 복구 세션을 지운다(인자 없음 = SDK 기본 global. scope 명시 여부는 Eng review D8에서 보류, 미해결). 그다음 "비밀번호를 바꿨어요" 화면과 `/`로 가는 링크를 보여준다. `signOut`은 `try/catch`로 감싸고, 실패해도 비밀번호는 이미 바뀌었으므로 `done`을 유지한다.

### 3. 수동 설정 (사용자)

- Supabase Dashboard → Authentication → URL Configuration → Redirect URLs에 위 두 URL을 추가한다.
- Authentication → Users → Add user로 테스트 계정을 만든다. 기본 SMTP는 조직 팀원 이메일로만 보내므로 **Supabase 조직 팀원 이메일**이어야 한다.

### 테스트

복구 링크 판정은 `recovery.test.ts`에 5행 표 테스트(일치 → true; `#type=recovery`만 + 세션 토큰 있음, `#type=recovery`만 + 세션 없음, 토큰 불일치, `#error=...otp_expired` → false)를 둔다(Eng review D4). 429 처리 규칙은 `request-result.test.ts` 3행으로 고정한다(Eng review D5). 나머지는 Supabase 호출과 UI 상태 전환이라 컴포넌트·E2E 도구 없이 수동으로 검증한다. 아래 Success Criteria의 수동 시나리오로 검증하고, 기존 `pnpm format:check && pnpm lint && pnpm test && pnpm build`가 통과해야 한다.

## Success Criteria

1. 테스트 계정(팀원 이메일)으로 요청하면 "메일을 확인해 주세요"가 뜨고 실제 메일이 온다.
2. 메일 링크 → `/reset-password`에서 폼이 보이고, 새 비밀번호를 저장하면 "비밀번호를 바꿨어요"가 뜬다. 새 비밀번호로 `signInWithPassword`(브라우저 콘솔)가 성공한다.
3. 가입되지 않은 이메일, 그리고 같은 가입 이메일로 곧바로 다시 요청해 429가 난 경우도 1과 같은 `"sent"` 화면을 보여준다.
4. 다음 경우 `invalid` 안내가 보인다. (a) 해시 없이 `/reset-password`에 직접 들어감. (b) 메일 속 링크를 다시 누름: 이 링크는 Supabase `/auth/v1/verify`를 거치고 일회용 토큰이라, 두 번째에는 `#error=...otp_expired`로 돌아온다. (c) 링크를 열고 저장하지 않은 채 떠났다가 해시 없이 다시 들어옴: 전용 메모리 클라이언트라 남은 세션이 없다(D6, D7). 리다이렉트된 `#access_token=...` URL을 토큰 유효 시간 안에 그대로 다시 여는 경우는 보장하지 않는다.
5. 네트워크를 끊고(DevTools Offline) 요청하면 오류 문구가 보이고 폼은 유지된다.
6. 확인 값이 다르면 버튼이 비활성화되고 불일치 문구가 보인다.
7. format/lint/test/build CI가 통과한다.
8. 두 탭에서 계정 A·B 링크를 각각 열고 A 탭에서 저장하면 A 비밀번호만 바뀐다(D6).
9. ready에서 헤더 링크로 이동했다가 뒤로가기하면 ready 폼이 유지된다(D9).
10. sent 화면의 "다른 이메일로 다시 받기"로 폼에 돌아가고 이메일이 유지된다. production 빌드에서 다른 페이지를 다녀온 뒤에도 같다(D10).
