## 스킬별 상세

### feature-dev

- **질문:** 범위(메일 발송 + 새 비밀번호 페이지), 설계 승인, 리뷰 결과 반영 여부. 모두 선택지형이라 답하기 쉬웠다.
- **계획:** 코드베이스와 `supabase-js` 내부 코드(flowType, PASSWORD_RECOVERY)를 직접 확인한 뒤 설계를 채팅으로 설명했다. 별도 문서는 남기지 않았다.
- **테스트:** lint, 타입체크, build 통과. 실제 메일 수신은 확인하지 않았다.
- **리뷰:** 리뷰 에이전트가 실제 보안 버그를 찾았다. 로그인 세션만 있으면 메일 링크 없이도 비밀번호를 바꿀 수 있었고, 이를 URL 해시 확인(`type=recovery`, `error` 없음) 2줄로 고쳤다.
- **품질:** 복구 링크일 때만 폼을 연다. 저장 후 로그아웃은 하지 않는다.

### superpowers

- **질문:** 열린 질문으로 시작해 방식, 범위(재설정만 연결, 테스트 계정은 대시보드), 시안 확인 순으로 대화했다.
- **계획:** 브라우저에 새 비밀번호 화면 시안을 띄워 확인받았다. "작은 변경"이라 설계 문서는 만들지 않았다.
- **테스트:** format, lint, test, build 통과. 실제 메일 수신은 확인하지 않았다.
- **리뷰:** 리뷰 에이전트 1회 후 반영했다.
- **품질:** 세션만 있으면 폼을 열어 링크 검증이 셋 중 가장 느슨하다. 저장 후 로그아웃은 한다. 시안 서버 파일(`.superpowers/brainstorm/`, 토큰 파일 포함)이 커밋에 들어갔다.

### gstack

- **질문:** /office-hours 12개, /plan-eng-review 13개, 이후 1개. 그중 7개는 업그레이드·벤더링·통계 같은 도구 설정이었다.
- **계획:**
  - 설계 문서(전제 5개, 접근법 3개)를 쓰고, 독립 리뷰어가 3라운드 검토했다. 품질 점수는 6 → 7 → 8로 올랐다.
  - 엔지니어링 리뷰에서 결정 10건 중 9건을 수락하고 1건(저장 후 로그아웃 범위)을 보류했다.
- **리뷰:** Codex 교차 리뷰가 다른 두 브랜치가 놓친 문제를 찾았다.
  - 공용 Supabase 클라이언트를 쓰면 다른 탭에서 연 계정의 비밀번호가 바뀔 수 있다.
  - `signOut()` 기본값이 모든 기기 로그아웃이다.
  - 메일 발송 완료 화면에 재시도 수단이 없다.
- **추가 발견:** Codex 지적을 검증하다 `cacheComponents` 때문에 뒤로가기 시 확인 로직이 다시 실행되는 문제도 찾았다.
- **결과물:** 리뷰가 끝난 뒤 Supabase 연동을 보류하기로 해서, UI(재시도 버튼, 저장 중 잠금, 비밀번호 확인)만 구현했다. 나머지 결정은 설계 문서(`docs/designs/password-reset.md`)와 `TODOS.md`에 남아 있다.

## 회고

1. **속도와 실행은 superpowers가 가장 좋았다.** 13분, 질문 5개로 연동까지 끝냈고 브라우저 시안이 직관적이었다. 대신 설계를 건너뛰어 링크 검증이 가장 느슨했고, 시안 서버 파일까지 커밋했다.
2. **균형은 feature-dev가 가장 좋았다.** 질문 4개로 범위를 확정했고, 리뷰 에이전트 1회로 실제 보안 버그를 잡아 2줄로 고쳤다.
3. **분석의 깊이는 gstack이 가장 깊었지만 무거웠다.** 교차 리뷰와 SDK 코드 검증으로 다른 브랜치가 놓친 문제들을 찾았다. 하지만 질문 26개, 66분을 쓰고도 커밋된 코드는 UI 약 100줄이라, 결과의 상당 부분이 다음 작업을 위한 문서로 남았다.
4. **세 브랜치 모두 새 자동 테스트와 실제 메일 수신 확인이 없었다.** 어떤 스킬을 써도 브라우저 QA와 E2E 검증은 따로 챙겨야 한다.
5. **작업 크기에 맞춰 고르는 게 맞다.** 작은 기능은 superpowers나 feature-dev가, 인증·보안처럼 놓치면 큰 작업은 gstack의 리뷰 단계만 골라 쓰는 조합이 효율적이다.
